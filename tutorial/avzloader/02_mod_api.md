# 模组 API

[文档目录](README.md) · [上一篇：模组加载与配置](01_configuration.md) · [下一篇：生命周期管理](03_lifecycle.md)

## 普通 AvZ 脚本如何成为模组

使用本仓库的头文件和 `libavz.a` 编译 32 位脚本 DLL。框架会自动提供 DLL 入口、加载器注册、逻辑与绘制回调，以及生命周期协议。原来的 `AScript`、协程、时间连接和帧运行接口仍然使用。

DLL 附加到进程时，会检查 `avzloader.dll` 是否存在。有加载器时取得加载器接口并注册为模组；没有加载器时安装原来的独立脚本钩子。加载器存在但所需接口不完整时，当前框架让 DLL 附加失败，而不会退回独立钩子覆盖加载器。

脚本作者通常不应重写 `DllMain`、`ModRunTotal` 等框架入口。自己接管这些入口会绕过注册、清理、绘制初始化保护等行为；若需要自定义协议实现，应遵守本文后半部分的约定。

## 脚本层接口

| 接口 | 模组中的用途 |
| --- | --- |
| `AScript`／协程脚本入口 | 按 AvZ 原有方式编写自动操作 |
| `ASetReloadMode` | 决定一次会话结束后是否重新运行脚本 |
| `ATickRunner`、时间连接、协程等待 | 注册业务回调；筛选不匹配时暂停框架调度 |
| `AOnBeforeScript`、`AOnAfterScript` | 每次脚本初始化前后设置或重置状态 |
| `AOnEnterFight`、`AOnExitFight` | 进入战斗，以及选卡／战斗会话结束时处理资源 |
| `AOnAfterInject`、`AOnBeforeExit` | 每次 DLL 加载的初始化，以及正常停止时的清理 |
| `ASetAdvancedPause`、`ASetUpdateWindow` | 通过加载器同步共享的游戏控制状态 |

状态钩的基本用法见[主库教程：状态钩](../26_state_hook.md)，重新运行设置见[载入脚本模式](../04_reload_mode.md)。加载器模式下的调用频率和停用行为以[生命周期管理](03_lifecycle.md)为准。

下面的脚本不需要实现额外的模组 API：

```cpp
#include <avz.h>

ATickRunner runner;
int ticks = 0;

AOnBeforeScript(ticks = 0);
AOnExitFight(runner.Stop());

void AScript() {
    ASetReloadMode(AReloadMode::MAIN_UI_OR_FIGHT_UI);
    runner.Start([] {
        ++ticks;
        // 在这里加入每个战斗运行帧的操作。
    });
}
```

框架会在会话结束时清理帧队列，上例的 `ExitFight` 用于展示作者清理的挂接位置。框架不会自动重置作者的所有全局变量，下一次运行所需的变量重置仍应写在 `BeforeScript` 或 `AScript` 中。

TOML 筛选由加载器实施，不需要在旧脚本中额外编写用户／关卡判断。当前没有新增面向脚本作者的“自主停用／恢复”回调 API。筛选改变、会话结束和最终停止的关系见生命周期文档。

## 模组导出协议

接口声明在 [`inc/avz_mod.h`](../../inc/avz_mod.h)，实现在 [`src/avz_mod.cpp`](../../src/avz_mod.cpp)。所有接口使用 `extern "C"`、`__declspec(dllexport)` 和 `__cdecl`。加载器按下面列出的名称使用 `GetProcAddress` 查找，因此符号名称、参数和调用约定都需要一致。

### 原有的八个必需导出

| 函数签名 | 作用与约定 |
| --- | --- |
| `void ModInit(HMODULE module)` | 记录当前 DLL 句柄。框架附加和目录加载路径都可能调用它，应保持可重复调用 |
| `void ModFinalize()` | 正常停止入口。当前模组路径请求停止并尝试维护，不在这里等待游戏线程完成整场战斗 |
| `void ModRunTotal()` | 执行业务逻辑；返回后再尝试推进延后的清理 |
| `void SyncControllerState(int sync, char* state)` | 读取或写入共享控制状态，布局见下文 |
| `int BlockTimeArrived()` | 表示同步阻塞等待是否到达目标时间；加载器据此在跳帧循环中让出控制 |
| `void BeforeDrawEveryTick()` | 绘制前准备与计时 |
| `void DrawEveryTick()` | 模组绘制和 `PAINT` 帧运行 |
| `void AfterDrawEveryTick()` | 绘制后的计时处理 |

加载器要求这八个函数全部存在。目录加载发现接口不完整时，会拒绝模组并释放本次加载获得的引用，不调用缺失的清理函数。已经由 injector 加载的 DLL 若接口不完整，则不会加入调度表；加载器不替 injector 释放它。

绘制入口不能假定 DLL 已执行过 `ModRunTotal`。热加载可能发生在本帧逻辑调度结束之后、绘制之前。当前框架在帧管理器尚未初始化或业务不允许运行时跳过三个绘制入口，基础绘制函数也检查初始化状态。

### 新的三个生命周期导出

这三个接口是加载器和框架之间的内部协议，普通脚本不需要实现或主动调用。

| 函数签名 | 作用与约定 |
| --- | --- |
| `void ModManage(int enabled, int user)` | 更新调度许可和当前用户 ID，观察会话变化，尝试清理。`enabled` 为零时仍需要调用它 |
| `void ModRequestStop()` | 设置最终停止请求。请求不等于完成，函数返回也不代表 DLL 已可卸载 |
| `int ModGetLifecycleState()` | 返回状态位组合，用于判断会话、等待、停止和清理失败 |

`ModManage` 的 `user` 是游戏内部的用户 ID；TOML 使用的用户名字符串由加载器匹配，两者作用不同。最终停止请求不会被下一次 `enabled = 1` 撤销，它也不等于一次可恢复的筛选停用。

加载器只有在三个接口全部存在时才启用生命周期协议。部分实现这三个接口不构成完整支持。停止确认必须在退出钩子、框架队列和协程清理完成，并且模组调用栈已退回后给出；具体卸载条件见下一篇。

### 生命周期状态位

状态声明在 [`inc/avz_mod_lifecycle.h`](../../inc/avz_mod_lifecycle.h)。它们是位掩码，可能同时出现，不是互斥枚举。

| 名称 | 值 | 含义 |
| --- | --- | --- |
| `AMOD_IDLE` | `0` | 没有已开始的会话，也没有其他标记；可能仍驻留或因筛选等待 |
| `AMOD_SESSION` | `1` | 存在选卡／战斗会话 |
| `AMOD_INITIALIZING` | `2` | 正在脚本初始化或模组调用栈尚未退出；不只指 `AScript` 正在执行 |
| `AMOD_WAIT_MAIN` | `4` | 按 `MAIN_UI` 模式等待关卡对象消失 |
| `AMOD_FINISHED` | `8` | 按 `NONE` 模式完成，不再开始新会话 |
| `AMOD_STOPPED` | `16` | 框架已完成停止，且调用深度为零、清理未失败 |
| `AMOD_FAILED` | `32` | 框架清理失败 |

加载器自身也记录导出调用失败，此时会禁用业务、标记失败并保留 DLL。因此不能仅依赖 DLL 返回的 `AMOD_STOPPED` 判断是否安全卸载。`AMOD_IDLE` 为零，不能用 `state & AMOD_IDLE` 判断空闲。

## 加载器提供的接口

模组框架通过 `ModInfo` 取得 `avzloader.dll` 的以下导出：

| 函数签名 | 用途 |
| --- | --- |
| `void RegisterMod(HMODULE module)` | 排队注册模块，由后续管理调度处理 |
| `void UnregisterMod(HMODULE module)` | 排队取消注册，移除调度记录；不调用 `FreeLibrary` |
| `void SetAdvancedPaused(int paused)` | 设置共享高级暂停状态，并记录当前请求所属模组 |
| `void SetUpdateWindow(int update)` | 设置共享窗口刷新状态，并记录禁用刷新请求所属模组 |
| `void LoaderRunTotal()` | 推进加载器管理、业务调度和状态同步；同步等待路径会使用它 |

注册队列只在短时间持有互斥锁，不在锁内调用 Windows 模块加载 API 或模组回调。目录加载时，DLL 自注册产生的命令也会被合并，不形成第二份相同句柄的调度记录。

这些接口同样使用 C 导出和 `__cdecl`。控制接口按当前正在调度的模组识别所有者，适合在框架回调中使用；从自建线程调用不会自动拥有同样的所有权上下文。该协议不承诺任意线程上的游戏操作安全。

## 控制状态同步

`SyncControllerState` 的 `state` 指向连续的三个 32 位 `int`，共 `12` 字节。传入内存需要满足 `int` 的对齐要求。

| 字节偏移 | 内容 | 加载器汇总方式 |
| --- | --- | --- |
| `0` | 高级暂停 | 共享状态，通过设置接口更新 |
| `4` | 跳帧请求 | 对所有可运行模组的请求按逻辑“或”合并 |
| `8` | 窗口刷新许可 | 共享状态，通过设置接口更新 |

`sync = 0` 时，模组将当前状态写到缓冲区；其中跳帧条件只有业务允许时才参与计算。加载器会检查每个可运行模组的条件，不能因前一个请求为真就跳过后续条件，因为条件完成可能触发作者回调。

`sync != 0` 时，当前框架读取偏移 `0` 和 `8`，同步高级暂停和窗口刷新。偏移 `4` 不会被写回模组来替换它自己的跳帧条件。

高级暂停和窗口刷新当前采用共享状态与单个所有者记录：后续生效的设置会覆盖前一次设置，不是每个模组各持一份请求再做引用计数。当前所有者筛选停用、会话结束、正常停止或注销时，加载器释放其控制状态；恢复匹配不会自动重新申请暂停或关闭刷新，需要脚本再次设置。

## 兼容范围与作者负责的资源

“兼容旧 DLL”指具备原有八个模组导出的 DLL 可以继续参与调度，不代表任意上游原版预编译脚本都具备这些导出。缺少完整生命周期协议的 DLL，加载器可以按筛选停止外部调度，但不能代替其内部框架执行新的会话清理和等待取消，目录热卸载也不会强制释放。

当前框架会清理它管理的队列和协程；作者自行创建的线程、安装到其他模块的回调、原始函数指针、独立游戏补丁等仍需要作者管理。正常停止时，应在可用的退出钩子中解除对 DLL 代码的外部引用，再允许卸载。游戏进程退出时不会调用这些脚本钩子，不能把进程退出的数据保存只放在 `BeforeExit` 中。
