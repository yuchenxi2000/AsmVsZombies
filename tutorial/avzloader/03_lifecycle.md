# 生命周期管理

[文档目录](README.md) · [上一篇：模组 API](02_mod_api.md) · [下一篇：开发与验证](04_development.md)

## 管理调度与业务调度

加载器把模组管理和业务回调分开。每次加载器逻辑调度先检查目录、用户／关卡和会话变化，再调用允许运行的模组，汇总控制状态，最后尝试处理可完成的卸载。

| 状态 | DLL 驻留 | 业务调度 | 管理调度 |
| --- | --- | --- | --- |
| 已加载、匹配、生命周期允许运行 | 是 | 是 | 是 |
| 筛选不匹配 | 是 | 否 | 是 |
| 等待回主菜单 | 是 | 否 | 是 |
| 运行完成并停止 | 是，除非另有目录卸载请求 | 否 | 是 |
| 目录卸载等待清理 | 是 | 否 | 是 |
| 清理或导出调用失败 | 保留 | 否 | 清理失败不重试作者清理；导出失败后停止该模组管理调用 |
| 已卸载 | 否 | 否 | 否 |

这里的业务包括 `AScript`、业务状态钩、时间连接、帧运行、绘制和跳帧条件。停止业务调度不会自动卸载 DLL。作者的自建线程和框架之外的游戏钩子不属于这个调度范围。

## DLL 加载与首次初始化

目录来源模组依次经历配置解析、`LoadLibraryW`、必需导出校验和登记。DLL 的 C++ 全局构造及 `DllMain` 在加载时执行，早于首个 AvZ 业务逻辑帧，因此全局构造函数不能假定帧管理器、日志器或关卡数据已经可用。

首次业务许可到来后，`GlobalInit` 建立基础日志器和帧管理器。`AfterInject` 在基础初始化后的业务路径中执行，每次 DLL 加载只执行一次。它不是 `DllMain` 回调，也不是 DLL 已加入进程就必定立即执行的通知。筛选一直不匹配时，DLL 可以驻留而从未执行 `AfterInject` 或 `AScript`。

随后，框架在满足 `MemoryInit` 条件时开始一次会话：

1. 游戏在选卡或战斗界面，关卡对象存在。
2. 排除禅境花园，以及关卡结束倒计时等不适合初始化的情况。
3. 执行注册的初始化操作，建立会话身份。
4. 执行 `BeforeScript`、`AScript`、`AfterScript`，再按界面执行相应运行帧和进入战斗逻辑。

因此“已加载”不保证“脚本已经执行”，筛选匹配也不保证当下可以开始 `AScript`。

### 绘制初始化保护

某个 DLL 可能在逻辑调度末尾才加载，紧接着收到同一帧的绘制回调。当前框架在基础帧管理器为空时跳过绘制前、绘制和绘制后入口，基础绘制函数也做相同检查。绘制不会反过来触发 `GlobalInit`。

保护条件针对基础初始化；它不承诺第一次绘制之前已经完成整个同步选卡或所有作者初始化步骤。作者的绘制数据若依赖 `AScript` 完成，仍应管理自己的准备状态。

## 筛选停用与恢复

当前用户／关卡不再匹配时，加载器保留 DLL，并将业务许可关闭。框架的业务钩、队列和跳帧条件不会继续执行，但 `ModManage` 仍观察这局游戏是否结束。

对于已经完成初始化、仍处于同一有效会话的模组，仅改变筛选配置不会执行 `ExitFight`、`BeforeExit` 或重新执行 `AScript`。时间连接、帧运行和挂起协程保留。同一局恢复匹配后，继续使用原来的状态。

游戏本身仍可能推进时钟，所以这种恢复不等于把游戏时间暂停在停用时刻。加载器不补放停用期间错过的业务帧；时间连接到达或超过目标时如何处理，仍遵循 AvZ 原有队列语义。

停用时会释放当前属于该模组的高级暂停和不刷新窗口请求。恢复匹配只恢复业务许可，不自动还原这两个请求。

### 初始化或同步等待中的例外

`ASelectCards`、`AWaitForFight` 等同步路径仍可能保留调用栈并推进游戏。收到停用、卸载或会话结束请求后，框架在游戏函数已经返回的 AvZ C++ 边界检查状态并取消等待，不让内部取消异常穿越游戏汇编调用。

尚未完成的脚本初始化不能在下一次匹配时从任意中间语句恢复，因此这次初始化会按会话结束处理。此时筛选改变可能带来 `ExitFight` 和旧队列清理；这与“已经初始化完毕的同一局仅暂停业务”不同。

作者自己编写、不调用可取消等待路径的无限循环不会被强行中断。若回调不返回，管理和卸载可能无法继续；没有强制卸载超时。

## 会话身份与结束条件

一次会话从选卡或战斗初始化开始，记录关卡对象地址、关卡 ID、用户 ID 及游戏时钟。选卡进入战斗属于同一次会话。

管理逻辑观察到下列任一情况时，将旧会话标记为结束：

| 条件 | 典型场景 |
| --- | --- |
| 关卡对象消失 | 返回主菜单 |
| 界面离开选卡／战斗 | 退出当前游戏流程 |
| 关卡对象地址改变 | 新建关卡或加载了另一局 |
| 关卡 ID 或用户 ID 改变 | 换模式、切换用户 |
| 已进入战斗后再次出现选卡界面 | 无尽下一轮或重新选卡，即使对象地址复用 |
| 已进入战斗，战斗时钟回退 | 读档、重开等复用对象的情况 |

这些条件是当前实现的会话判定方式，不是对所有游戏修改版的通用识别保证。只要管理调度还在执行，即使模组因配置停用，也会观察并处理这些变化。

## 会话清理与重新运行

框架在模组调用深度回到零后结束会话，执行一次 `ExitFight`，然后清理或重置以下状态：

| 内容 | 会话结束时的处理 |
| --- | --- |
| 挂起协程 | 通过框架退出钩子销毁，清理其句柄记录 |
| 时间连接／操作队列 | 清空，并取消队列初始化状态 |
| `GLOBAL`、`ONLY_FIGHT`、`PAINT` 帧队列 | 清空，避免旧回调进入下一局 |
| 绘制队列 | 通过绘制器退出钩子清理；字体资源按绘制器实现处理 |
| 同步阻塞状态和每局运行标记 | 重置 |
| 快速进出游戏的请求和倒计时 | 重置 |
| `AFTER_INJECT` 帧队列 | 会话结束时保留，最终停止时才清空 |
| 作者的其他全局变量 | 不自动重置，由作者管理 |

保留的 `AFTER_INJECT` 队列仍受业务许可约束；它并不在筛选停用、等待主菜单或最终停止时绕过调度限制。

### `ASetReloadMode` 在模组中的含义

| 模式 | 旧会话结束后的行为 |
| --- | --- |
| `NONE`（默认） | 标记运行完成，执行最终停止清理，不再运行下一局；DLL 可继续驻留 |
| `MAIN_UI` | 等待关卡对象消失，再允许下一次满足条件的初始化 |
| `MAIN_UI_OR_FIGHT_UI` | 不要求先回主菜单；下一次满足条件时可以开始新会话 |

`MAIN_UI` 的实现依据是“关卡对象已消失”，并非只检查一个主菜单 UI 编号。等待解除后，仍须满足筛选和初始化条件。

模组路径中，`AScript` 返回后不再用一个阻塞循环等待整场战斗结束；后续由加载器推进业务和会话管理。同步选卡和 `AWaitForFight` 的功能仍保留。未通过加载器运行的独立注入路径保留原来的整场等待行为。

## 状态钩的调用范围

| 钩子 | 模组模式下的范围 |
| --- | --- |
| `AfterInject` | 每次 DLL 加载后的首次允许业务路径执行一次，基础初始化已完成 |
| `BeforeScript`／`AfterScript` | 每次脚本初始化前后；取消初始化时后续钩子可能不执行 |
| `EnterFight` | 会话进入战斗后的业务路径执行；仍受筛选限制 |
| `BeforeTick`／`AfterTick` | 业务逻辑调度前后；受到停用或取消影响，不能依赖两者总是成对 |
| `ExitFight` | 已开始的会话结束时执行，包括从选卡直接退回主菜单；不受筛选停用阻止 |
| `BeforeExit` | 正常最终停止时执行一次，前提是这次 DLL 的 `AfterInject` 已开始；不受筛选停用阻止 |

业务钩列表在每个钩子之间重新检查业务许可。若前一个钩子导致停用或会话变化，后续业务钩会停止执行。清理钩仍需要能够完成；重复管理不会重复执行同一次会话或停止的清理钩。

退出时关卡对象可能已经消失，所以 `ExitFight` 应主要释放作者持有的资源。需要读取游戏内存时，必须先判断当前对象是否仍存在，不能继续使用旧会话缓存的指针。

## 目录模组的安全卸载

目录扫描发现 DLL 消失或写入时间变化后，设置卸载请求。后续流程为：

```text
目录变化 → pendingUnload → 停止业务调度 → ModRequestStop
       → 管理逻辑结束旧会话并执行最终清理
       → 返回 AMOD_STOPPED → 到达安全释放位置 → FreeLibrary
```

最终清理会结束有效会话，执行符合条件的 `BeforeExit`，清理所有框架协程和操作队列，并清空四种帧队列，包括 `AFTER_INJECT`。即使没有有效会话，也会尝试清理 DLL 初始化阶段可能注册的资源。

加载器调用 `FreeLibrary` 前同时要求：

1. 模组由目录加载，且确实有卸载请求。
2. 三个生命周期接口完整，状态包含 `AMOD_STOPPED`。
3. 没有清理失败，也没有加载器记录的导出调用失败。
4. 该模组没有活动导出调用，加载器的外层调度深度也已经归零。

框架自己的调用深度也参与停止确认。这样即使同步选卡或等待期间重入加载器、提前收到清理请求，也不会在旧回调尚未返回时销毁其队列或卸载正在执行的代码。绘制的前／中／后阶段另有一层整体调度保护。

注册记录使用稳定容器，注销先停止调度，在安全位置移除记录。旧 DLL 的注销命令会在重新加载之前处理，避免 Windows 复用句柄时把旧注销误应用于新模块。

卸载没有“等够若干毫秒就强行释放”的分支。旧 DLL 缺少协议、作者回调未返回或清理失败时，会停留在等待／保留状态。接口或清理异常的捕获针对 C++ 调用失败，不能据此认为任意内存访问异常都会被隔离。

## injector 所有权与进程退出

injector 注入的模块由外部工具持有加载所有权。加载器只负责登记和调度，不因目录变化替它调用 `FreeLibrary`；替换注入仍使用原有工具流程。

游戏进程退出与普通热卸载分开处理。`DllMain` 收到进程终止的分离通知时，会提前设置退出标记并清空帧管理器访问指针，然后让 CRT 执行全局对象析构。此时不调用脚本的 `ExitFight`／`BeforeExit`，不等待游戏线程，也不访问已被游戏销毁的对象。

默认帧句柄处于已停止状态，停止状态查询也检查帧管理器是否存在。因此一直被筛选阻止、从未初始化的模组，其全局收集器等对象仍可安全析构；已初始化模组的析构也不会再次查询可能已销毁的帧队列或日志器。

加载器 DLL 自身被固定驻留至进程退出，保证游戏钩子和目录监控使用的代码地址有效。退出通知只发出监控停止信号，不在 Windows 加载器锁内等待线程或执行作者清理。
