# 模组加载与配置

[文档目录](README.md) · [下一篇：模组 API](02_mod_api.md)

## 文件布局

加载器根据游戏可执行文件所在目录定位 `mods`，扫描其中的 DLL；不会递归扫描子目录。第一次进入加载器主循环时会尝试创建这个目录。

```text
游戏目录/
├── PlantsVsZombies_modded.exe
├── avzloader.dll
└── mods/
    ├── pe12.dll
    ├── pe12.toml
    ├── lazy.dll
    └── advpause.dll
```

配置文件和 DLL 同名，只将最后的扩展名改为 `.toml`。例如，`script.dll` 对应 `script.toml`。没有配置文件时不附加用户／关卡限制，但是否执行 `AScript` 仍取决于框架的初始化条件和重新载入模式。

多个脚本应使用不同的 DLL 文件名。加载器没有依赖声明或显式的模组排序配置，不应依赖目录枚举顺序实现模组之间的初始化依赖。

## 两种加载来源

| 来源 | 加载方式 | TOML 配置 | 卸载所有权 |
| --- | --- | --- | --- |
| `mods` 目录 | 加载器调用 `LoadLibraryW` | 读取目录中的同名配置 | 加载器确认清理后调用 `FreeLibrary` |
| `injector` 注入 | 外部工具加载 DLL，DLL 向加载器注册 | 当前注册路径不读取同名配置 | 由 injector 的原有替换注入流程负责 |

目录扫描只管理目录来源的模组。清空 `mods` 不会卸载由 injector 注入的 DLL。希望用 TOML 限制用户／关卡并支持目录热卸载时，应把模组放在 `mods` 中。

## 热加载与更新 DLL

新增 DLL 后，加载器在后续游戏逻辑调度中发现并加载。移走 DLL，或者将后缀改为不再匹配 `.dll`，会请求停止并卸载。

```text
script.dll → script.dll.disabled
```

只把 `script.dll` 改成 `script2.dll`，文件仍会被视为待加载模组。Windows 对已加载 DLL 的文件操作存在限制，更新时按以下顺序操作：

1. 将原 DLL 移出 `mods`，或改为 `.dll.disabled` 等后缀。
2. 等待框架完成清理和卸载；调试输出中的 `Unload mod:` 表示加载器已进入释放模块的步骤。
3. 将新 DLL 放回 `mods`。需要保留筛选规则时，保留与新 DLL 同名的 TOML。

加载器也会比较文件的最后写入时间，发现变化后请求重新加载，但这不意味着可以直接覆盖已加载的 DLL。若显示 `Unload pending:`，先根据[开发与验证文档](04_development.md)判断等待原因。

配置文件支持热更新。修改配置只改变调度许可，不重新加载 DLL，也不在同一有效会话中重新执行 `AScript`。

## 用户和关卡规则

```toml
[[run]]
[run.user]
include = "Ycx"
[run.level]
include = 13
```

这条规则要求用户名为 `Ycx`，并且关卡 ID 为 `13`。用户名按字符串精确匹配，区分大小写；关卡使用游戏中的关卡 ID，不是当前波数。`13` 是本仓库 `pe12` 示例使用的泳池生存无尽关卡。

规则支持单个值和数组：

```toml
[[run]]
[run.user]
include = ["Ycx", "666"]
[run.level]
include = [13, 14]
```

也可以改用排除规则：

```toml
[[run]]
[run.user]
exclude = "233"
[run.level]
exclude = [20, 24]
```

同一个 `user` 或 `level` 表中，`include` 和 `exclude` 只能使用一种；用户和关卡可以分别选择不同的模式。用户值必须是字符串，关卡值必须是整数，数组中的每个元素都必须符合对应类型。

| 配置 | 含义 |
| --- | --- |
| `include = 值或数组` | 只允许列出的值 |
| `exclude = 值或数组` | 允许未列出的值 |
| 未设置某个维度 | 不限制该维度 |
| `include = []` | 该条规则在此维度永不匹配 |
| `exclude = []` | 不排除任何值；若出现在 `level` 中，仍有下面的界面限制 |

只要一条规则设置了 `level.include` 或 `level.exclude`，这条规则就只在选卡界面（UI `2`）或战斗界面（UI `3`）参与匹配。主菜单可能保留旧的关卡 ID，加载器不会因此让这条规则匹配主菜单。

只限制用户、没有限制关卡的模组，可以在匹配用户的其他界面获得业务调度，例如运行 `AfterInject`。不过普通 `AScript` 仍需满足选卡／战斗等条件，详见[生命周期管理](03_lifecycle.md)。

## 多条规则的组合

同一个 `[[run]]` 内，用户条件与关卡条件是“并且”；多个 `[[run]]` 之间是“或者”。

```toml
[[run]]
[run.user]
include = "Ycx"
[run.level]
include = 13

[[run]]
[run.user]
include = "666"
[run.level]
include = 14
```

上例允许 `Ycx` 在关卡 `13` 运行，或 `666` 在关卡 `14` 运行。不要再附加一条没有条件的 `[[run]]`，否则这条规则会匹配所有用户／界面，让整体配置不再限制运行。

没有 `run` 项、没有任何运行规则，或者删除整个配置文件，均表示不附加筛选限制。框架只校验已实现的配置结构和选项，不提供任意未知键的完整诊断；拼错字段名可能使预期限制没有生效，应在游戏内检查匹配效果。

## 配置失败与目录监控

已有模组的配置会先完整解析、校验，再替换旧配置。TOML 语法错误、`include`／`exclude` 同时存在、值类型错误等情况会保留上一次有效配置。不会把一次保存中的不完整文件当作“无限制运行”。

首次加载时没有旧配置可用，因此配置无效会跳过该 DLL；修复后，后续扫描会重试。删除配置文件是有效操作，表示恢复无限制运行，不按解析失败处理。

目录监控线程只记录变化，不在该线程上执行模组回调或加载／卸载。主循环采用约 `200 ms` 的防抖，并每 `2 s` 补扫一次，覆盖监控失败或遗漏通知的情况。这些间隔决定扫描时机，不是卸载完成的时限；游戏线程不再调度时，扫描和清理也无法继续推进。

成功扫描到空目录或确认目录不存在时，会请求卸载目录来源的模组。访问失败等扫描错误则保留原快照和已登记模组，避免把“读不到目录”误认为“用户移走了所有 DLL”。
